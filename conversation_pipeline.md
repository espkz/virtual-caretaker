# Conversation pipeline (current Django implementation)

This documents the active implementation in `vipdjango/vip`. The intended architecture is a single scenario-driven conversation service: fixed scenario text is emitted by the application, natural dialogue is generated by the LLM, and LangGraph owns lifecycle state. The repository also contains an older, unused response helper in `vip/views.py`; the path below is the one used by the current chat request flow.

```text
scenario prompt (.md)
        |
        v
parse_scenario_prompt -> structured Scenario
        |
        v
ConversationEngine.respond -> LangGraph state
        |                         initialize -> generate -> finalize
        v
system/context builder + history -> OpenAI LLM
        |
        v
character response + voice metadata + completion
        |
        v
ChatMessage history / ChatSession -> browser rendering -> TTS
```

## Files and responsibilities

- `prompts/*.md` are role/scenario prompts. The checked-in scenarios include `scenario_1_ai_daughter_caregiver_training_prompt.md`, `scenario_2_ai_daughter_hospice_communication_prompt.md`, `caregiver_prompt.md`, and `peggy_collins_prompt.md`.
- `prompts/prompt_template.md` is the global prompt prefix and contains the shared roleplay rules plus an application-owned, non-dialogue Post-Conversation Protocol note.
- `vipdjango/vip/prompt_utils.py` normalizes headings, splits `##` Markdown sections, resolves aliases, and extracts fixed protocol content.
- `vipdjango/vip/conversation_scenario.py` parses a role prompt into the immutable `Scenario` dataclass: character, learner, main/introduction voice fields, Introduction, Opening Line, Beginning/Middle/Ending guidance, cues, Closing, and meta instructions.
- `vipdjango/vip/conversation_graph.py` defines `ConversationState` and the three-node LangGraph (`initialize`, `generate`, `finalize`). It carries dialogue and voice metadata separately, treats a forward model-selected stage as the semantic transition signal, and defines a soft `TARGET_TURNS = 20` plus a later operational safety cap (`MAX_TURNS = 24`).
- `vipdjango/vip/conversation_engine.py` is the production conversation service. It performs semantic stop classification, emits fixed text at lifecycle boundaries, builds LLM context, invokes the graph, and returns dialogue separately from normalized voice metadata.
- `vipdjango/vip/views.py` creates `ConversationEngine`, supplies the global template prefix and API key, persists dialogue/voice metadata, carries the stage across requests, and renders chat/TTS responses. `ChatSession` and `ChatMessage` are defined in `vipdjango/vip/models.py`.
- `vipdjango/vip/tests/` contains unit tests for parsing, prompts, graph lifecycle, and the engine. `manual_conversation.py` is the developer terminal harness; it adds no conversation policy.

## Prompt and parsing flow

The global prompt is the shared behavioral contract from `prompt_template.md` (identity, boundaries, output format, and protocol). The role prompt is scenario-specific and authoritative for the character, learner role, background, stage guidance, cues, fixed text, and voice. `ConversationEngine._system_prompt()` combines the global prompt with the parsed scenario and current state; it does not treat the role prompt as a replacement for the global prompt.

`parse_scenario_prompt()` reads Markdown headings through alias matching. Missing optional sections receive safe defaults (female voice, natural speech, or nursing student); unknown genders fall back to female. `Scenario.to_state()` supplies the dictionary stored in LangGraph state.

## State, nodes, and lifecycle

`ConversationState` carries the scenario, complete native LLM history, current/target/max turn counts, remaining budget, stage/phase, response, separate voice metadata, stage-transition readiness, completion flags, interrupt flags, and debug information. `ChatSession.conversation_stage` and `conversation_phase` carry the active lifecycle across HTTP requests. `initialize` fills lifecycle defaults and rejects turns beyond the safety cap. `generate` calls the injected response function (the LLM adapter), accepts a monotonic forward stage selected by that adapter, and records response, stage, voice metadata, completion, interruption, and debug data. `finalize` does not force completion at the soft target or substitute a fixed Closing at the safety boundary.

The application lifecycle is:

1. With zero learner messages, `respond()` returns the scenario Introduction exactly.
2. The learner message is checked by a small semantic interrupt LLM. An explicit stop can complete immediately; this is not keyword-based ending logic.
3. On learner turn one, the fixed Opening Line is returned when present.
4. Later turns invoke the LangGraph and LLM. The persisted stage starts in Beginning and changes when the model selects a later stage based on the semantic purpose of the current conversation; there are no numeric stage thresholds. The context also contains a derived ledger of answered character questions so the model can acknowledge and move on instead of replaying them. The soft-turn phases provide normal conversation through turn 10, increasing resolution guidance through turn 17, and closure preference around turns 18–22 only when the scenario is actually ready to end.
5. A natural LLM completion uses the fixed Closing when one exists, but only after a semantic transition to Ending. Reaching turn 20 does not complete the conversation, and reaching the later operational safety boundary does not substitute the Closing merely because of the counter.
6. The global template says the application owns any post-conversation notice. The view does not append that notice as a second assistant dialogue row, so it cannot enter conversational history or TTS.

The approximately 20-turn budget is soft: turns 1–10 are normal conversation, turns 11–17 add resolution guidance, and turns 18–22 add closure preference only when semantic ending cues are satisfied. `MAX_TURNS` is 24, so the engine can continue beyond turn 20 when necessary; the later boundary is operational only and does not create a conversational ending.

## Context, history, and voice

`_history()` maps the complete persisted transcript to native `user` and `assistant` roles and removes only legacy trailing voice annotations from assistant content. The LLM payload is one system message from `_system_prompt()` followed by that history. It includes immutable assistant/learner identity blocks, all stage guidance, current semantic cues, derived answered-question memory, meta instructions, current turn, soft target, safety cap pressure, the scenario’s voice gender/style, and a JSON output contract. If a draft repeats an answered question, the engine makes one targeted repair request and uses a no-question acknowledgment only as a last-resort boundary fallback. The LLM returns dialogue, a style description, stage, transition readiness, completion, and interrupt fields. The engine normalizes voice metadata to `female voice, emotional/style description` without brackets; `ChatMessage.voice_metadata` stores it separately from dialogue. Legacy embedded annotations are removed at the dialogue boundary for history, display, and TTS.

The database preserves the transcript in `ChatMessage` rows under `ChatSession`; `ChatMessage.content` contains dialogue and `ChatMessage.voice_metadata` contains voice metadata. `ChatSession` also stores the current stage, lifecycle phase, and completion state. The frontend views render assistant/student dialogue and expose TTS controls; the terminal tester keeps the same in-memory message sequence and writes voice metadata per message in its JSON artifact.

## Debugging points

- Parser mismatch: inspect `split_markdown_sections()` and the exact headings in the scenario file.
- Wrong fixed text or stage: inspect `ConversationEngine.respond()` before `graph.invoke()`.
- Context/history: enable Python logging for `vip.conversation_engine` or run the tester with `--verbose`.
- Lifecycle: inspect `initialize`, `_phase_for_turn`, `generate`, and `finalize` in `conversation_graph.py`.
- Persistence/TTS: inspect the chat POST flow and the shared `split_dialogue_and_voice()` boundary used by history, rendering, and TTS.
- Stop behavior: `_interrupt()` is semantic classification; do not add phrase/keyword ending rules to production.

## Run tests and the terminal tester

From the repository root:

```bash
cd vipdjango
python manage.py migrate
python -m unittest discover -s vip/tests -p 'test_*.py'
python vip/tests/manual_conversation.py
python vip/tests/manual_conversation.py --scenario ../prompts/scenario_1_ai_daughter_caregiver_training_prompt.md --verbose
```

The tester requires `OPENAI_API_KEY` for a live run. It lists existing `prompts/*_prompt.md` scenarios, preserves production `ConversationEngine` behavior, and supports `/help`, `/status`, `/save`, and `/stop`. Completed conversations auto-save under `test_conversations/` (or `--output-dir`). A future scripted mode can be added without changing the engine; no learner-response LLM is used today.
