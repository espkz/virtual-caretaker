# Conversation pipeline (current Django implementation)

This documents the active implementation in `vipdjango/vip`. The intended architecture is a single scenario-driven conversation service: fixed scenario text is emitted by the application, natural dialogue is generated by the LLM, and LangGraph owns lifecycle state. The repository also contains an older, unused response helper in `vip/views.py`; the path below is the one used by the current chat request flow.

```text
scenario prompt (.md)
        |
        v
parse_scenario_prompt -> structured Scenario
        |
        v
ConversationEngine.respond -> LangGraph state
        |                         initialize -> generate -> finalize
        v
system/context builder + history -> OpenAI LLM
        |
        v
character response + voice metadata + completion
        |
        v
ChatMessage history / ChatSession -> browser rendering -> TTS
```

## Files and responsibilities

- `prompts/*.md` are role/scenario prompts. The checked-in scenarios include `scenario_1_ai_daughter_caregiver_training_prompt.md`, `scenario_2_ai_daughter_hospice_communication_prompt.md`, `caregiver_prompt.md`, and `peggy_collins_prompt.md`.
- `prompts/prompt_template.md` is the global prompt prefix and contains the shared roleplay rules plus an application-owned, non-dialogue Post-Conversation Protocol note.
- `vipdjango/vip/prompt_utils.py` normalizes headings, splits `##` Markdown sections, resolves aliases, and extracts fixed protocol content.
- `vipdjango/vip/conversation_scenario.py` parses a role prompt into the immutable `Scenario` dataclass: character, learner, main voice settings, Introduction, Opening Line, Beginning/Middle/Ending guidance, cues, Closing, and meta instructions.
- `vipdjango/vip/conversation_graph.py` defines `ConversationState` and the three-node LangGraph (`initialize`, `generate`, `finalize`). It carries dialogue and voice metadata separately, treats a forward model-selected stage as the semantic transition signal, and defines a soft `TARGET_TURNS = 20` plus a later operational safety cap (`MAX_TURNS = 24`).
- `vipdjango/vip/conversation_engine.py` is the production conversation service. It performs semantic stop and ending classification, emits fixed text at lifecycle boundaries, builds LLM context, invokes the graph, and returns dialogue separately from normalized voice metadata. On the voice path it can consume a Responses API stream without changing the graph state contract.
- `vipdjango/vip/views.py` creates `ConversationEngine`, supplies the global template prefix and API key, persists dialogue/voice metadata, carries the stage across requests, and renders chat/TTS responses. Voice submissions can use an SSE response and short streamed TTS requests; the ordinary POST and complete-message TTS endpoints remain available as fallbacks. `ChatSession` and `ChatMessage` are defined in `vipdjango/vip/models.py`.
- `vipdjango/vip/voice_timing.py` records trace-scoped browser/server marks for latency analysis without putting timing data in the conversation state.
- `vipdjango/vip/tests/` contains unit tests for parsing, prompts, graph lifecycle, and the engine. `manual_conversation.py` is the developer terminal harness; it adds no conversation policy.

## Prompt and parsing flow

The global prompt is the shared behavioral contract from `prompt_template.md` (identity, boundaries, output format, and protocol). The role prompt is scenario-specific and authoritative for the character, learner role, background, stage guidance, cues, fixed text, and voice. `ConversationEngine._system_prompt()` combines the global prompt with the parsed scenario and current state; it does not treat the role prompt as a replacement for the global prompt.

`parse_scenario_prompt()` reads Markdown headings through alias matching. Missing optional sections receive safe defaults (female voice, natural speech, or nursing student); unknown genders fall back to female. `Scenario.to_state()` supplies the dictionary stored in LangGraph state.

## State, nodes, and lifecycle

`ConversationState` carries the scenario, complete native LLM history, current/target/max turn counts, remaining budget, stage/phase, response, separate voice metadata, stage-transition readiness, completion flags, interrupt flags, and debug information. `ChatSession.conversation_stage` and `conversation_phase` carry the active lifecycle across HTTP requests. `initialize` fills lifecycle defaults and rejects turns beyond the safety cap. `generate` calls the injected response function (the LLM adapter), accepts a monotonic forward stage selected by that adapter, and records response, stage, voice metadata, completion, interruption, and debug data. `finalize` does not force completion at the soft target or substitute a fixed Closing at the safety boundary.

The application lifecycle is:

1. Starting a new chat creates a session and persists the scenario Introduction as the first assistant text-only message. It has no voice metadata or TTS controls.
2. The learner message is checked by a small semantic interrupt LLM. An explicit stop can complete immediately; this is not keyword-based ending logic.
3. On learner turn one, the fixed Opening Line is returned after the learner's greeting; older sessions with a previously seeded Opening Line remain backward compatible.
4. Later turns invoke the LangGraph and LLM. The persisted stage starts in Beginning and changes when the model selects a later stage based on the semantic purpose of the current conversation; there are no numeric stage thresholds. The context also contains a derived ledger of answered character questions so the model can acknowledge and move on instead of replaying them. The soft-turn phases provide normal conversation through turn 10, increasing resolution guidance through turn 17, and closure preference around turns 18–22 only when the scenario is actually ready to end.
5. A natural LLM completion uses the fixed Closing when one exists, but only after a semantic transition to Ending. If a middle/ending response looks like a possible endpoint, the engine runs a conservative semantic ending verifier; it compares meaning with the ending guidance and treats the canonical Closing as an example, not an exact string. Reaching turn 20 does not complete the conversation, and reaching the later operational safety boundary does not substitute the Closing merely because of the counter.
6. The global template says the application owns any post-conversation notice. The view does not append that notice as a second assistant dialogue row, so it cannot enter conversational history or TTS.

The approximately 20-turn budget is soft: turns 1–10 are normal conversation, turns 11–17 add resolution guidance, and turns 18–22 add closure preference only when semantic ending cues are satisfied. `MAX_TURNS` is 24, so the engine can continue beyond turn 20 when necessary; the later boundary is operational only and does not create a conversational ending.

## Context, history, and voice

`_history()` maps the complete persisted transcript to native `user` and `assistant` roles and removes only legacy trailing voice annotations from assistant content. The LLM payload is one system message from `_system_prompt()` followed by that history. It includes immutable assistant/learner identity blocks, all stage guidance, current semantic cues, derived answered-question memory, meta instructions, current turn, soft target, safety cap pressure, the scenario’s voice gender/style, and a JSON output contract. If a draft repeats an answered question, the engine makes one targeted repair request and uses a no-question acknowledgment only as a last-resort boundary fallback. Possible endpoint responses receive a separate conservative semantic ending check, with its result and reason included in debug information and logs. The LLM returns dialogue, a style description, stage, transition readiness, completion, and interrupt fields. The engine normalizes voice metadata to `female voice, emotional/style description` without brackets; `ChatMessage.voice_metadata` stores it separately from dialogue. Legacy embedded annotations are removed at the dialogue boundary for history, display, and TTS.

The database preserves the transcript in `ChatMessage` rows under `ChatSession`; `ChatMessage.content` contains dialogue, `ChatMessage.voice_metadata` contains voice metadata, and `ChatMessage.pipeline_timing` contains the merged client/server timestamps and derived durations for that turn. `ChatSession` also stores the current stage, lifecycle phase, completion state, the active learner-turn claim, and the last completed turn ID. A retry with the same turn ID reclaims an uncompleted learner row instead of inserting another row; each generation attempt also has a server-side claim token so late cancellation/error cleanup cannot release a replacement attempt. Assistant persistence requires the matching claim and checks the latest transcript row while holding the session lock. The frontend views render assistant/student dialogue and expose TTS controls; the terminal tester keeps the same in-memory message sequence and writes voice metadata per message in its JSON artifact.

## Voice latency path and instrumentation

The current browser microphone path is `SpeechRecognition`, not an OpenAI file-upload STT request. It receives interim/final transcript results while the microphone is active, applies conservative capitalization/terminal punctuation only to the final transcript, and submits that value after recognition ends. The baseline server path then waits for the complete model response, redirects, downloads a complete TTS response into a blob, and starts playback. Regular playback reuses the message's audio element and replaces only the request-owned source; streaming playback creates one short-lived audio element per ordered sentence and waits for its terminal event before advancing.

When browser streaming is available, a voice submission includes `voice_timing`, a client-generated `turn_id`, and requests `text/event-stream`. The server keeps the same scenario parsing, history, LangGraph invocation, structured response schema, persistence, anti-repetition repair, ending verifier, and normalized voice metadata. The Responses API stream is parsed only far enough to expose the dialogue string incrementally; the final structured object remains authoritative. The stream callback is forwarded through a live queue after the parallel stop-intent check resolves; text may display before graph completion, but sentence audio is held until the final post-repair response has been persisted. This prevents a provisional draft from starting TTS and then competing with its repair response. SSE events carry the turn ID and a monotonic sequence; the browser ignores stale or repeated events and invalidates active chunk audio when a reset/new turn arrives. The database also atomically accepts one pending learner turn and commits at most one assistant response for that turn.

The trace is logged as JSON by `VoicePipelineTiming`. Browser marks include `recording_start`, `recording_end`, `stt_start`, `stt_completion`/`stt_finalization`, `response_display`, `tts_text_first_usable`, `first_tts_audio_data`/`tts_first_audio_chunk`, `audio_playback_start`, and `client_pipeline_complete`. Server marks include `gpt_request_start`, `gpt_first_output`, `response_complete`, `gpt_completion`, `tts_request_start`, `tts_first_audio_data`/`tts_first_audio_chunk`, `tts_completion`, and `client_report_received`. Use the same trace ID to calculate:

- speech end to transcript completion: `stt_completion - recording_end` (browser marks);
- transcript completion to first GPT output: `gpt_first_output - stt_completion`;
- GPT output to first audible audio: `audio_playback_start - gpt_first_output` using the epoch timestamps from the same trace;
- speech end to first audible response: `audio_playback_start - recording_end`.

The server logs the non-streaming fallback too, so unsupported browsers and older requests remain measurable. `VoicePipelineTiming` also emits the derived durations in `durations_ms`; `response_complete` is response generation/persistence completion, while `client_pipeline_complete` is the end of queued browser playback work. `VOICE_PIPELINE_LATENCY_REPORT.md` records the first real-browser sample: six complete voice traces from `test_conversations/chat_session_37.txt`. It identifies the LLM request and the post-first-output-to-usable-TTS span as the largest measured startup contributors, while noting that the current marks do not split response completion, repair, and endpoint verification. That sample has no recording/STT marks, so microphone latency remains unmeasured; numeric before/after optimization claims still require additional same-trace logs with representative real speech. The test suite validates the timing and streaming handoff but cannot measure network/model latency offline.

The baseline remains available for comparison: complete-response GPT plus redirect and complete-response TTS. The streaming voice path streams GPT text over SSE, then starts sentence-bounded TTS requests from the persisted authoritative response and streams each TTS response with chunked audio. Typed submissions use the same SSE/TTS path as microphone submissions when the browser supports readable response streams; the ordinary POST remains a fallback. Both OpenAI emotion TTS and the gTTS no-emotion fallback return chunked audio responses. The browser tracks each sentence index once per stream, so a repeated SSE event cannot start duplicate audio; cancelling the active chunk also resolves its queue wait before the next stream begins. The seeded Introduction is application-owned text and has no TTS path; the Opening Line is emitted after the learner's first turn.

## Debugging points

- Parser mismatch: inspect `split_markdown_sections()` and the exact headings in the scenario file.
- Wrong fixed text or stage: inspect `ConversationEngine.respond()` before `graph.invoke()`.
- Context/history: enable Python logging for `vip.conversation_engine` or run the tester with `--verbose`.
- Lifecycle: inspect `initialize`, `_phase_for_turn`, `generate`, and `finalize` in `conversation_graph.py`.
- Persistence/TTS: inspect the chat POST flow and the shared `split_dialogue_and_voice()` boundary used by history, rendering, and TTS.
- Stop behavior: `_interrupt()` is semantic classification; do not add phrase/keyword ending rules to production.

## Run tests and the terminal tester

From the repository root:

```bash
cd vipdjango
python manage.py migrate
python -m unittest discover -s vip/tests -p 'test_*.py'
python vip/tests/manual_conversation.py
python vip/tests/manual_conversation.py --scenario ../prompts/scenario_1_ai_daughter_caregiver_training_prompt.md --verbose
```

The tester requires `OPENAI_API_KEY` for a live run. It lists existing `prompts/*_prompt.md` scenarios, preserves production `ConversationEngine` behavior, and supports `/help`, `/status`, `/save`, and `/stop`. Completed conversations auto-save under `test_conversations/` (or `--output-dir`). A future scripted mode can be added without changing the engine; no learner-response LLM is used today.
