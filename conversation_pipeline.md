# Conversation pipeline (current Django implementation)

This documents the active implementation in `vipdjango/vip`. The intended architecture is a single scenario-driven conversation service: fixed scenario text is emitted by the application, natural dialogue is generated by the LLM, and LangGraph owns lifecycle state. The repository also contains older compatibility helpers in `vip/views.py`; the path below is the one used by the current chat request flow.

```text
scenario prompt (.md)
        |
        v
parse_scenario_prompt -> structured Scenario
        |
        v
ConversationEngine.respond -> LangGraph state
        |                         initialize -> generate -> finalize
        v
system/context builder + history -> OpenAI LLM
        |
        v
character response + voice metadata + completion
        |
        v
ChatMessage history / ChatSession -> browser rendering -> TTS
```

## Files and responsibilities

- `prompts/role_*.md` are role/scenario prompts; `prompts/role_prompt.md` is the authoring template. Production normally stores an uploaded or edited copy in `RolePrompt.content`.
- `prompts/global_prompt.md` is the source of shared behavior and instructions. `_extract_template_prefix()` loads it unchanged for the conversation engine; the selected role prompt supplies scenario-specific context and behavior.
- `vipdjango/vip/prompt_utils.py` normalizes headings, splits `##` Markdown sections, resolves aliases, and extracts fixed protocol content.
- `vipdjango/vip/conversation_scenario.py` parses a role prompt into the immutable `Scenario` dataclass: character, background context, learner, main voice settings, Introduction, Opening Line, Beginning/Middle/Ending guidance, cues, optional generic objectives, Closing, and meta instructions.
- `vipdjango/vip/conversation_graph.py` defines `ConversationState` and the three-node LangGraph (`initialize`, `generate`, `finalize`). It carries dialogue and voice metadata separately, carries generic objective progress and recent topics, treats a forward model-selected stage as the semantic transition signal, and defines a soft `TARGET_TURNS = 20` plus a later operational safety cap (`MAX_TURNS = 24`).
- `vipdjango/vip/conversation_engine.py` is the production conversation service. It performs semantic stop and ending classification, emits fixed text at lifecycle boundaries, builds LLM context, invokes the graph, and returns dialogue separately from normalized voice metadata.
- `vipdjango/vip/views.py` creates `ConversationEngine`, supplies the global prompt and API key, persists dialogue/voice metadata and objective progress, carries lifecycle state across requests, and renders chat/TTS responses. Each turn completes LLM generation before the corresponding complete TTS response is requested. `ChatSession` and `ChatMessage` are defined in `vipdjango/vip/models.py`.
- `vipdjango/vip/voice_timing.py` records trace-scoped browser/server marks for latency analysis without putting timing data in the conversation state.
- `vipdjango/vip/tests/` contains unit tests for parsing, prompts, graph lifecycle, and the engine. `manual_conversation.py` is the developer terminal harness; it adds no conversation policy.

## Phase 1 audit findings

The verified current architecture is:

1. A browser request enters `professor_test_chat()` or `student_dashboard()`, which delegates to `_chat_dashboard()` in `views.py`. The selected `RolePrompt` is loaded from the database; its `content` is the scenario/role prompt. The terminal harness in `vip/tests/manual_conversation.py` instead reads a prompt file from `prompts/`.
2. `_extract_template_prefix()` loads `prompts/global_prompt.md` from the repository and passes it to `ConversationEngine`. The engine does not read files or database rows itself. The production generation path uses `parse_scenario_prompt()` and the engine's `_history()`.
3. `parse_scenario_prompt()` calls `split_markdown_sections()`, which recognizes `##` headings after normalization. Alias lookup supplies the `Scenario` dataclass fields and defaults missing optional values. An optional Conversation Objectives section is parsed into generic objective records with stable IDs, possible expressions, and resolution guidance. `Scenario.to_state()` converts that immutable parsed configuration into the dictionary carried by LangGraph.
4. For a learner turn, `_chat_dashboard()` persists the learner `ChatMessage`, supplies the prior `ChatSession.conversation_stage`, `conversation_phase`, and `completion_status`, and calls `_generate_assistant_response()`. `ConversationEngine.respond()` counts persisted learner messages, handles the zero-turn Introduction and first-turn Opening Line boundary cases, builds the graph input, and invokes `initialize -> generate -> finalize`.
5. `initialize` fills the turn budget fields, phase, stage defaults, objective progress defaults, and lifecycle flags. `generate` calls `_llm_turn()`; the engine returns dialogue, normalized voice metadata, a proposed stage, validated objective progress, completion, interrupt state, and debug data. The graph accepts only a monotonic stage change and preserves the response state. `finalize` recomputes remaining turns but does not force completion. The view persists the assistant row and writes the resulting stage, phase, objective progress, and completion state back to `ChatSession`.
6. A normal generation request sends one system message followed by native `assistant`/`user` history. The system message contains the global prefix, immutable scenario character and learner role, the active stage guidance and its transition cues, optional objective definitions and progress, recent learner topics, scenario meta instructions, voice settings, derived answered-question memory, lifecycle/turn-budget state, and the JSON output contract. The same turn can conditionally add one repair request for an answered-question repetition or one semantic ending-verifier request for a possible endpoint. The first learner turn can make a separate semantic interrupt request before the fixed Opening Line; later normal turns use `stop_requested` in the main structured response.
7. Conversation history is stored as `ChatMessage` rows under `ChatSession`. `_history()` maps student rows to native `user` messages and assistant rows to native `assistant` messages, prefixes their serialized content with generic `LEARNER:` or `SIMULATED CHARACTER:` labels, strips only trailing legacy voice annotations from assistant content, omits the application-owned Introduction when the scenario is known, and retains the remaining spoken transcript. Voice metadata is stored separately in `ChatMessage.voice_metadata`; it is not part of dialogue history.
8. Beginning/Middle/Ending is not selected by numeric turn thresholds. The persisted stage starts at Beginning, and the LLM proposes a semantic forward stage using the active behavioral guidance and transition cues. The graph prevents regression. Turn count only selects pressure phases (`normal`, `resolution_guidance`, `closure_preference`, `closure_flexibility`) and enforces the later operational `MAX_TURNS` boundary.
9. Transition cues are currently evaluated by the generation model from the cue text in the system prompt; there is no separate deterministic cue parser. Completion requires a model-requested completion together with a semantic transition to Ending, or a conservative ending verifier for a candidate endpoint. A supplied Closing replaces the generated dialogue only after completion. An explicit stop can complete immediately, while the view rejects new non-retry turns after the safety cap. Reaching the soft target does not itself advance a stage or end the conversation.

## Phase 1 failure-mode diagnosis

The retained transcripts and current implementation support these findings:

- **One-theme loops:** `test_conversations/rachel_ellison_prompt_20260817_133010.txt` and `test_conversations/chat_session_46.txt` remain centered on recovery, awareness, prognosis, and long-term care across many learner turns. Those historical prompts do not define the new optional objective section, so their old runs had no objective ledger. Configured scenarios now expose covered and unresolved objectives to the model; stage alone still cannot select a new concern when a scenario has not defined objectives.
- **Repeated addressed questions:** the engine derives `_answered_questions()` from whether a later learner message looks substantive, then uses a conservative lexical `_question_similarity()` threshold to detect repetition. Semantically similar paraphrases with different vocabulary (for example, whether the character will wake up versus the realistic chance of meaningful recovery) can evade that check. Configured objectives now provide a second, semantic progress signal, but the model still determines whether a learner response reasonably addresses an objective and the lexical guard remains a fallback.
- **Unrelated questions:** there is no structured scenario-boundary or objective check after generation. The global prompt explicitly permits additional questions not written in the script, and the stage prompt contains broad scenario facts and possible questions. That gives the model room to invent a plausible-sounding extension. The retained logs do not provide a clean confirmed example of an unrelated question, so this remains an implementation risk to validate with a cross-scenario test rather than a claim about every logged response.
- **Learner-role confusion:** the system prompt explicitly maps the assistant to the scenario character and the user to the learner, so the retained logs do not show a confirmed role swap. The audit identified two scenario-specific leaks—an absent `Learner Role` defaulted to `nursing student`, and the repetition repair instruction named Rachel. Those are now replaced with the generic `the learner in this simulation` fallback and `the simulated character` wording. Native API roles remain required, and serialized history now also carries generic simulation-speaker labels.
- **Speaking as the learner:** no retained transcript clearly shows the model speaking for the learner. The current protection is prompt-level prohibition only; the structured response schema has no speaker-ownership field and there is no post-generation role validator. A malformed response could therefore still pass through if the model violates the instruction.
- **History labels:** the original `_history()` representation preserved native API `user` and `assistant` roles but did not add literal simulation-speaker labels, which was a plausible contributor to role ambiguity in long contexts. It now retains those native roles and prefixes serialized content with generic `LEARNER:` or `SIMULATED CHARACTER:` labels. The formatter is idempotent at the LLM request boundary, so direct callers with unformatted native history receive the same representation without duplicate labels. The system prompt defines the relationship between the API roles and simulation labels, and tests cover all three checked-in scenario types.
- **Redundant or conflicting prompt instructions:** role ownership and output-format rules appear both in the global template prefix and in `_system_prompt()`. The template's post-conversation protocol is placed after `{role}` and is silently excluded by `_extract_template_prefix()`, creating a source/runtime mismatch. The unused legacy parser in `views.py` also has different aliases and field names from `parse_scenario_prompt()`. These are maintainability and fidelity risks even where they do not yet produce a visible failure.
- **LLM-dependent stage/cue/objective inference:** cue and objective evaluation are delegated to the generation model in one structured response. The graph validates stage monotonicity and the engine validates objective IDs and keeps covered progress monotonic, but it does not independently determine whether a cue was satisfied or whether the learner addressed a concern. This is an intentional lightweight progress layer; stronger semantic evaluation would be a separate design decision.

The diagnosis led to a small Phase 2 ownership fix, a Phase 3 history-clarity fix, and the bounded Phase 4–5 objective/progress layer: the runtime now uses explicit `SIMULATED CHARACTER` and `LEARNER` wording, scenario-specific identities remain in parsed scenario data, missing learner-role data has a generic fallback, serialized history carries generic speaker labels while preserving native API roles, and optional objectives persist as validated progress state. Tests cover the Rachel scenario plus caregiver and patient scenarios. Objective inference remains model-assisted by design; broad refactoring is not justified by this audit alone.

## Prompt and parsing flow

The global prompt is the shared behavioral contract from `global_prompt.md` (identity, boundaries, and progression behavior). The role prompt is scenario-specific and authoritative for the character, learner role, background, goals, stage guidance, cues, fixed text, and voice. `ConversationEngine._system_prompt()` combines the global prompt with parsed scenario reference data, the active stage, and current state; it does not send the raw role Markdown as a second instruction block. Native history roles are retained for the API, while each serialized history entry also carries a generic simulation-speaker label.

`parse_scenario_prompt()` reads Markdown headings through alias matching. Missing optional sections receive safe defaults (female voice, natural speech, or `the learner in this simulation`); unknown genders fall back to female. An optional `Conversation Objectives`/`Objectives`/`Goals` section contains one `###` or `OBJECTIVE:` block per concern, with optional `Possible expressions:` and `Resolved when:` guidance. The parser assigns stable generic IDs from the headings. `Scenario.to_state()` supplies the dictionary stored in LangGraph state.

## State, nodes, and lifecycle

`ConversationState` carries the scenario, complete native LLM history, active/covered/unresolved objective IDs, recent topics, ending readiness, current/target/max turn counts, remaining budget, stage/phase, response, separate voice metadata, stage-transition readiness, completion flags, interrupt flags, and debug information. `ChatSession` persists the objective fields alongside `conversation_stage` and `conversation_phase` so progress survives HTTP requests. `initialize` fills lifecycle and objective defaults and rejects turns beyond the safety cap. `generate` calls the injected response function (the LLM adapter), accepts a monotonic forward stage selected by that adapter, validates and carries objective progress from debug data, and records response, stage, voice metadata, completion, interruption, and debug data. `finalize` does not force completion at the soft target or substitute a fixed Closing at the safety boundary.

The phase contract is generic: Beginning establishes rapport and the character's immediate concern, with no minimum duration; Middle uses unresolved objectives and the learner's latest meaning to select the next relevant concern; Ending is available when the scenario endpoint is naturally ready and important concerns have been addressed or can be acknowledged appropriately. The model may move forward early, change objectives out of order, or wrap an unresolved objective when it reports `ending_ready`. The engine rejects completion when important objectives remain unresolved without that readiness signal, while preserving the soft turn budget as pressure rather than a forced ending rule.

The application lifecycle is:

1. Starting a new chat creates a session and persists the scenario Introduction as the first assistant text-only message. It has no voice metadata or TTS controls.
2. The learner message is checked by a small semantic interrupt LLM. An explicit stop can complete immediately; this is not keyword-based ending logic.
3. On learner turn one, the fixed Opening Line is returned after the learner's greeting; older sessions with a previously seeded Opening Line remain backward compatible.
4. Later turns invoke the LangGraph and LLM. The persisted stage starts in Beginning and changes when the model selects a later stage based on the semantic purpose of the current conversation; there are no numeric stage thresholds. When configured, objective progress starts with all objective IDs unresolved, and each structured response can mark multiple concerns covered, preserve unresolved concerns, select an active unresolved concern, and report ending readiness. The context also contains a derived ledger of answered character questions so the model can acknowledge and move on instead of replaying them. The soft-turn phases provide normal conversation through turn 10, increasing resolution guidance through turn 17, and closure preference around turns 18–22 only when the scenario is actually ready to end.
5. A natural LLM completion uses the fixed Closing when one exists, but only after a semantic transition to Ending. If a middle/ending response looks like a possible endpoint, the engine runs a conservative semantic ending verifier; it compares meaning with the ending guidance and treats the canonical Closing as an example, not an exact string. Reaching turn 20 does not complete the conversation, and reaching the later operational safety boundary does not substitute the Closing merely because of the counter.
6. The global template says the application owns any post-conversation notice. The view does not append that notice as a second assistant dialogue row, so it cannot enter conversational history or TTS.

The approximately 20-turn budget is soft: turns 1–10 are normal conversation, turns 11–17 add resolution guidance, and turns 18–22 add closure preference only when semantic ending cues are satisfied. `MAX_TURNS` is 24, so the engine can continue beyond turn 20 when necessary; the later boundary is operational only and does not create a conversational ending.

## Context, history, and voice

`_history()` maps spoken persisted transcript rows to native `user` and `assistant` roles, prefixes the serialized content with generic `LEARNER:` or `SIMULATED CHARACTER:` labels, and removes only legacy trailing voice annotations from assistant content. The application-owned Introduction is already represented by the scenario and is omitted from later LLM history; all spoken history remains available for emotional and semantic continuity. The LLM payload is one system message from `_system_prompt()` followed by that history. It includes immutable assistant/learner identity, the mapping between native API roles and simulation labels, parsed scenario background reference, active-stage character guidance and its transition cues, optional objective definitions and progress, recent learner topics, scenario meta instructions, derived answered-question memory, current lifecycle state, voice settings, and the JSON output contract. Raw role Markdown is parsed before entering LangGraph and is not re-injected into the system message, preventing learner-facing headings and instructions from competing with the character contract. The global contract permits off-script responses only when directly relevant and prohibits invented roles, unrelated scenarios, unrelated educational objectives, and filler questions. If a draft repeats an answered question, the engine makes one targeted repair request and uses a no-question acknowledgment only as a last-resort boundary fallback. Possible endpoint responses receive a separate conservative semantic ending check, with its result and reason included in debug information and logs. The LLM returns dialogue, a style description, stage, transition readiness, completion, interrupt state, active objective, covered/unresolved objective IDs, and ending readiness. The engine normalizes voice metadata to `female voice, emotional/style description` without brackets; `ChatMessage.voice_metadata` stores it separately from dialogue. Legacy embedded annotations are removed at the dialogue boundary for history, display, and TTS.

The database preserves the transcript in `ChatMessage` rows under `ChatSession`; `ChatMessage.content` contains dialogue, `ChatMessage.voice_metadata` contains voice metadata, and `ChatMessage.pipeline_timing` contains the merged client/server timestamps, derived durations, and per-request `llm_context` size measurements for that turn. Each context measurement records the request kind (`interrupt`, `generation`, `repair`, or `semantic_ending_verifier`), message count, content and serialized payload sizes, a clearly labeled token estimate, and provider-reported token usage when the API returns it. `ChatSession` also stores the current stage, lifecycle phase, completion state, active objective, covered and unresolved objective IDs, recent topics, ending readiness, the active learner-turn claim, and the last completed turn ID. A retry with the same turn ID reclaims an uncompleted learner row instead of inserting another row; each generation attempt also has a server-side claim token so late cancellation/error cleanup cannot release a replacement attempt. Assistant persistence requires the matching claim and checks the latest transcript row while holding the session lock. The frontend views render assistant/student dialogue and expose TTS controls; the terminal tester keeps the same in-memory message sequence and writes voice metadata per message in its JSON artifact.

## Voice latency path and instrumentation

The current browser microphone path is `SpeechRecognition`, not an OpenAI file-upload STT request. It receives interim/final transcript results while the microphone is active, applies conservative capitalization/terminal punctuation only to the final transcript, and submits that value after recognition ends. The server waits for the complete model response, persists it, redirects, downloads one complete TTS response into the message audio element, and starts playback. On normal turns, semantic stop intent comes from the structured response instead of a second classifier request. The first fixed Opening Line still uses the classifier because there is otherwise no generation request to carry that decision; conditional repair and ending-verifier calls remain available for their separate correctness duties. Each `ConversationEngine` reuses one OpenAI client for those calls.

The trace is logged as JSON by `VoicePipelineTiming`. Browser marks include `recording_start`, `recording_end`, `stt_start`, `stt_completion`/`stt_finalization`, `response_display`, `tts_text_first_usable`, `first_tts_audio_data`/`tts_first_audio_chunk`, `audio_playback_start`, and `client_pipeline_complete`. Server marks include `gpt_request_start`, `gpt_first_output`, `response_complete`, `gpt_completion`, `tts_request_start`, `tts_first_audio_data`/`tts_first_audio_chunk`, `tts_completion`, and `client_report_received`. Use the same trace ID to calculate:

- speech end to transcript completion: `stt_completion - recording_end` (browser marks);
- transcript completion to first GPT output: `gpt_first_output - stt_completion`;
- GPT output to first audible audio: `audio_playback_start - gpt_first_output` using the epoch timestamps from the same trace;
- speech end to first audible response: `audio_playback_start - recording_end`.

`VoicePipelineTiming` emits derived durations in `durations_ms`; `response_complete` is response generation/persistence completion. `VOICE_PIPELINE_LATENCY_REPORT.md` records the prior real-browser sample for latency comparison. The current reliability path intentionally favors one complete response and one complete audio payload per turn, so responses cannot overlap or arrive out of order. The seeded Introduction is application-owned text and has no TTS path; the Opening Line is emitted after the learner's first turn.

## Debugging points

- Parser mismatch: inspect `split_markdown_sections()` and the exact headings in the scenario file.
- Wrong fixed text or stage: inspect `ConversationEngine.respond()` before `graph.invoke()`.
- Context/history: enable Python logging for `vip.conversation_engine` or run the tester with `--verbose`.
- Lifecycle: inspect `initialize`, `_phase_for_turn`, `generate`, and `finalize` in `conversation_graph.py`.
- Persistence/TTS: inspect the chat POST flow and the shared `split_dialogue_and_voice()` boundary used by history, rendering, and TTS.
- Stop behavior: `_interrupt()` is semantic classification; do not add phrase/keyword ending rules to production.

## Run tests and the terminal tester

From the repository root:

```bash
cd vipdjango
python manage.py migrate
python -m unittest discover -s vip/tests -p 'test_*.py'
python vip/tests/manual_conversation.py
python vip/tests/manual_conversation.py --scenario ../prompts/role_rachel_ellison_1.md --verbose
```

The tester requires `OPENAI_API_KEY` for a live run. It lists the scenario files under `prompts/role_*.md`, preserves production `ConversationEngine` behavior, and supports `/help`, `/status`, `/save`, and `/stop`. Completed conversations auto-save under `test_conversations/` (or `--output-dir`). A future scripted mode can be added without changing the engine; no learner-response LLM is used today.
