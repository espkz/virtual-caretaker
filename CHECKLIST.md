# Task Checklist

## How to Use This Checklist

- Work through items in order unless an item depends on later investigation.
- Mark an item `[x]` only after it has actually been implemented and verified.
- Keep incomplete items as `[ ]`.
- Do not mark an item complete merely because code was written; test the behavior.
- If an item reveals a larger problem, add a sub-item rather than silently skipping it.
- Do not rewrite completed items unless a regression requires it.
- If the session ends because of context limits, the next session should inspect this file and continue from the first unchecked item.
- Do not attempt to complete the entire checklist in one session.

# Phase 1 — Reliability

## Prevent duplicate responses

- [x] Inspect the complete learner-turn pipeline.
- [x] Identify whether multiple LLM requests can be triggered by one learner utterance.
- [x] Ensure each learner turn receives a unique turn/request ID.
- [x] Ensure only one response can be committed for a learner turn.
- [x] Prevent stale LLM responses from replacing newer responses.
- [x] Ensure cancelled requests cannot commit their results.
- [x] Ensure conversation history is updated exactly once per turn.

## Prevent duplicate audio

- [x] Inspect the TTS request lifecycle.
- [x] Identify whether multiple TTS requests can exist for one assistant response.
- [x] Ensure an assistant response produces exactly one intended audio stream.
- [x] Ensure audio playback cannot accidentally start twice.
- [x] Ensure replacing/cancelling a response does not leave orphaned audio playback.

## Audio interruption

- [x] Determine why audio sometimes cuts off.
- [x] Check whether frontend state updates interrupt playback.
- [x] Check whether audio elements are recreated while playing.
- [x] Check whether a newer response cancels an older audio stream.
- [x] Check whether cleanup logic is cancelling valid playback.
- [x] Fix the underlying cause.
- [x] Verify uninterrupted playback during normal responses.

# Phase 3 — Reduce Latency

## Prompt/context efficiency

- [ ] Measure the size of the actual LLM context sent on each turn.
- [ ] Identify redundant information.
- [ ] Identify information that must remain available every turn.
- [ ] Identify information that can be represented as structured state.
- [ ] Identify information that can safely be omitted from later turns.
- [ ] Reduce unnecessary context without weakening character fidelity.
- [ ] Re-measure latency after context changes.
- [ ] Verify roleplay behavior has not regressed.

## Backend/request efficiency

- [ ] Identify unnecessary processing between STT, LLM, and TTS.
- [ ] Remove unnecessary round trips where practical.
- [ ] Avoid duplicate serialization/deserialization.
- [ ] Reuse persistent connections where appropriate.
- [ ] Remove unnecessary waiting between pipeline stages.
- [ ] Re-measure latency.

# Phase 4 — Streaming LLM → TTS

## LLM streaming

- [ ] Determine whether the current LLM implementation can stream output.
- [ ] Enable LLM streaming if appropriate.
- [ ] Detect usable sentence/clause boundaries in streamed text.
- [ ] Avoid sending incomplete fragments to TTS unnecessarily.
- [ ] Ensure streamed chunks remain in the correct order.
- [ ] Ensure partial/stale responses cannot be committed.

## TTS streaming

- [ ] Determine whether the current TTS implementation supports streaming audio.
- [ ] Stream the first usable text segment to TTS without waiting for the complete response.
- [ ] Begin audio generation as early as safely possible.
- [ ] Queue subsequent audio chunks.
- [ ] Ensure audio chunks remain ordered.
- [ ] Prevent gaps caused by unnecessary waiting.

Target behavior:

    User finishes speaking
            ↓
       STT final
            ↓
       LLM begins
            ↓
    first usable text
            ↓
       TTS begins
            ↓
      audio begins
            ↓
    later LLM text continues
            ↓
    later TTS audio is queued

# Phase 5 — Continuous Audio Playback

- [ ] Inspect the current sentence-by-sentence playback implementation.
- [ ] Determine whether audio chunks can be queued without recreating playback unnecessarily.
- [ ] Implement an audio playback queue if needed.
- [ ] Pre-buffer upcoming audio where practical.
- [ ] Minimize gaps between chunks.
- [ ] Ensure playback feels like one continuous response.
- [ ] Preserve natural pauses and sentence boundaries.
- [ ] Avoid abruptly cutting off the previous chunk.
- [ ] Test short responses.
- [ ] Test long responses.
- [ ] Test responses containing multiple sentences.
- [ ] Test network/stream interruptions.

Target user experience:

    Character thinks briefly
            ↓
    character starts speaking
            ↓
    speech continues naturally
            ↓
    next audio is already available
            ↓
    no obvious sentence-by-sentence gaps

# Phase 6 — Speech Recognition

## Current browser SpeechRecognition

- [ ] Verify interim and final results are handled correctly.
- [ ] Prevent duplicate final transcripts.
- [ ] Ensure only finalized learner speech triggers the LLM.
- [ ] Improve capitalization where practical.
- [ ] Improve punctuation where practical.
- [ ] Keep punctuation processing lightweight.
- [ ] Do not send every interim transcript to an LLM for punctuation.
- [ ] Verify transcript cleanup does not alter meaning.

## Realtime transcription investigation

- [ ] Determine whether the current STT is limiting latency.
- [ ] Determine whether continuous transcription would improve turn detection.
- [ ] Determine whether interruption/barge-in is needed.
- [ ] Investigate Realtime transcription architecture.
- [ ] Compare expected benefits against implementation complexity.
- [ ] Only migrate if the investigation shows a meaningful benefit.

- [ ] One assistant response produces exactly one intended audio stream.
- [ ] Stale responses cannot overwrite current responses.
- [ ] Audio does not unexpectedly cut off.
- [ ] Latency has been measured and major bottlenecks addressed.
- [ ] LLM output can begin flowing into TTS before the entire response finishes.
- [ ] Audio chunks can play continuously with minimal gaps.
- [ ] Speech recognition produces clean finalized utterances.
- [ ] Realtime transcription has been evaluated rather than adopted unnecessarily.
- [ ] Character fidelity remains intact.
- [ ] Conversation progression remains natural.
- [ ] The system remains stable under repeated conversations.
- [ ] Code cleanup has been completed only after the architecture stabilized.
